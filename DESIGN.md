# cu-overlay design notes

## Why a helper process

Claude Desktop draws the Computer Use glow and cursor in a transparent Electron window. On Wayland an app window cannot be placed above everything, cannot be made click-through reliably, and cannot be positioned on another output. wlr-layer-shell's overlay layer gives exactly that, but Electron does not speak it. So the bridges (which already ship one static binary per session type) grow an `overlay` subcommand, and this crate is its shared implementation. GNOME's Mutter has no layer-shell; there the overlay uses XWayland override-redirect windows instead (the `x11` backend, below).

## Decisions

- **Surfaces.** One layer surface per show (overlay layer, anchored to all edges, exclusive zone -1, keyboard interactivity none, empty input region, namespace `claude-cu-overlay`) carries the glow or rim. Three synchronized subsurfaces carry the badge, the press ring and the arrow, stacked in that order (empty input regions too). Moving the arrow redraws only a 192 px logical buffer and its position lands atomically with the parent commit; the ring is separate so it stays at the press point while the arrow glides away, as upstream's `#cursor-press` does.
- **Confined to the shown output.** A wl_subsurface is not clipped to its parent, so a subsurface placed past the layer surface's edge is drawn on whatever output that lands on. Each subsurface box is therefore intersected with the output (`geom::sub_box`): a point that is not on the output unmaps the arrow or ring (the controller keeps the pose, so `move` to the right output shows it again), and a box that straddles the edge gets a smaller buffer cut at the edge, positioned at the clipped origin, with the anchor moved inside it. Cutting the buffer (rather than a viewport source rectangle) works with and without wp_viewporter and keeps the surface itself inside the output, so nothing can spill; the only cost is that a drop shadow near the cut does not see the silhouette beyond it, which is invisible because that part is off the output anyway. One non-fatal `arrow outside output <name>` error per command tells the caller its point was not drawn.
- **Badge.** `badge.rs` mirrors upstream's `#badge` CSS and its `badge-center-to-corner` keyframes (5 % in, hold to 88 %, slide to the corner, ends at opacity 0; one `cubic-bezier(0.4, 0, 0.2, 1)` per keyframe interval, applied to opacity, `top`/`left`, the `translate(-50%, -50%)` and the scale together) and the dot's `dot-pulse`. Timing is pure functions of the milliseconds since the `show`, so the controller only keeps a start instant and the backend places the pill from the output size. The pill is painted with tiny-skia (pill path, border as an even-odd ring, dot) and the text with `ab_glyph` outlines of one embedded subset of Noto Sans Medium (OFL 1.1).
  - *Font rasterizer, not a mask.* A pre-rendered alpha mask of the English string would be a few KB but fixes the text, the size and the scale: the pill is drawn at 1.4 x the output scale, shrinks continuously to 0.8 during the slide and must be crisp at any fractional scale, and callers can pass a localized string (`badgeText`). Rasterizing 30 glyphs per frame costs microseconds, so no glyph cache is needed. The price is about 150 KB of code and a 34 KB font (Basic Latin to Cyrillic, no kerning); the alternative of a runtime system-font lookup would need fontconfig (C) and is not static.
  - *One surface, drawn per frame.* The subsurface keeps the size of the pill at its largest scale for the whole flash (so its buffers are reused), and the pill is drawn inside it at the current scale and sub-pixel offset; the box follows the pill in whole logical pixels, clamped to the output (a box that does not fit the output is not drawn), so it never reaches a neighbouring output. The slide and flash-in are paced by frame callbacks, the hold by the 30 Hz timer the glow pulse uses (the dot is the only thing that changes), and after 6 s the surface is blanked and nothing runs. Opacity (flash fade times the layer's fade times a capture hide) goes through the alpha modifier when there is one, else it is baked into the pixels.
  - *Capture.* The badge is part of scope `all` (the scene's opacity is 0, the surface is blanked) and not of scope `cursor`: it is not a cursor and it is short-lived, and the rim or glow it belongs to stays too. A caller that must keep it out of every screenshot sends `all`.
  - *Reduced motion* never shows it (upstream leaves `#badge` at opacity 0 there). Every `show` restarts the flash or, without `badge`, clears it, as upstream's page does on each show.
- **Subsurfaces are blanked, not unmapped.** To hide the arrow or ring (off the output, capture hide, ring finished) the overlay commits a fully transparent buffer of the same size in place instead of attaching null. On the first CI run (sway 1.9 / wlroots 0.17.1, ubuntu-24.04) an arrow unmapped by a null attach stayed on screen in two cases where the scene kept animating (a press running after an off-output jump, a glide continuing off the output), while every buffer commit repainted correctly; the exact sway 1.9 code path was not reproduced locally. A blanked subsurface stays mapped, invisible and click-through until its next draw, and is destroyed with the rest on `hide`.
- **No null attach on the layer surface.** Attaching a null buffer unmaps a layer surface and re-attaching later is a protocol error ("layer_surface has never been configured", seen in the prototype). `hide` destroys the surfaces after the fade, and a later `show` creates new ones; a capture hide without alpha-modifier attaches a 1x1 transparent buffer scaled up by the viewport.
- **Alpha modifier for opacity.** Fades, the glow pulse and the capture hide change `wp_alpha_modifier_surface_v1` multipliers and commit, with no redraw. The glow is drawn once at the pulse's peak keyframe and dimmed to 0.70 (the ratio of base to peak edge alpha) for the low point. The pulse commits at about 30 Hz on a timer; glides, presses and fades are paced by frame callbacks; nothing at all runs while the scene is static.
- **Glow math.** CSS inset box-shadow with blur `b` is a Gaussian with sigma b/2 (the CSS spec value; a measurement of upstream's own rendering on X11 matched it: alpha 0.52 / 0.20 / 0.044 at 0 / 50 / 100 px versus 0.55 / 0.19 / 0.045 from the model). The inside of the box blurred is separable, so each band is two 1D erf profiles; only the edge bands within 3.5 sigma are computed.
- **Arrow.** The transform reproduces upstream's element chain exactly (tilt pivot (2.2, 1.6) in viewBox units, 22 px SVG for 18 units at (-3, -2), bump around the hotspot, body scale 2 (1 + 0.06 lift)). drop-shadow's blur length is taken as the Gaussian's standard deviation (SVG `feGaussianBlur` semantics), approximated by three box blurs limited to the arrow's bounding box, with per-thread scratch buffers so a glide does not allocate.
- **Frames come from the caller.** The glide planner (duration from distance, arc, swing and lift springs) stays in the JS side, which already has upstream's function; the overlay plays `[x, y, deg, lift]` frames with linear interpolation, as WAAPI does with upstream's keyframes. The overlay therefore never needs updating when upstream retunes the motion.
- **Coordinates.** Protocol coordinates are global logical (what `screens` reports). Outputs come from `wl_output` (name, mode, transform) and `zxdg_output_v1` (logical position and size); the reported scale is mode / logical size, so 1.5 is exact. The buffer scale is the surface's `wp_fractional_scale_v1` preferred scale, else the output scale through the viewport, else the integer output scale.
- **Two capture scopes.** `all` zeroes every multiplier (or swaps in transparent buffers); `cursor` detaches only the arrow and ring subsurfaces, which takes effect with the parent commit, so the rim or glow never blinks. The scene simply leaves the cursor out while a hide is in force; the controller's clocks keep running, so `restore` draws the arrow at its current pose and the ring only if `press_frame` still has a frame for it. `ready` advertises `captureScopes` for feature detection.
- **Capture hide is acknowledged after a `wl_display.sync`** following the commit: the compositor has applied the zero multiplier (or transparent buffer) before any later screencopy or portal screenshot is rendered. It restores itself after 3 s so a caller that dies mid-screenshot never leaves the overlay invisible.
- **Unknown output on `show` is fatal**: exit 2 without surfaces. On `move` it is a non-fatal error and the overlay stays on its current output (a bridge should not need a respawn for a stale display id). An output unplugged while shown is not fatal either: `closed` from the compositor becomes a non-fatal error plus `hidden`.
- **Output layout is pushed.** `ready` lists every output (name, global logical position and size, scale); any later change (wl_output / xdg_output `done`, global removal) re-reads the list and sends an `outputs` event when it differs from the last one sent, so a bridge never has to query again.
- **Parent death** follows cu-abort-watch: `PR_SET_PDEATHSIG` plus a 500 ms check of `CLAUDE_CU_PARENT_PID` (pid + start time) or `getppid`. No signal handlers are needed: the compositor removes the surfaces with the connection on any exit.
- **Testability.** The controller takes `Instant`s as input, so every timing rule (fades, glide playback, ring keyframes, capture auto-restore) is unit tested without a compositor; the renderer is tested on raw buffers; the backend is tested end to end on a headless sway.

## X11 backend (GNOME/Mutter)

Measured on Ubuntu 25.04 (Mutter 48.1, Xwayland 24.1.6, VirtualBox, software rendering, two monitors: 1280x800 at scale 1 and 1600x1000 at 1.25).

- **Why XWayland.** Mutter has no layer-shell and no other protocol that puts a client surface above every window on a chosen output without focus. An X11 override-redirect window does: Mutter stacks it above normal and fullscreen windows, the top bar and the dock; it is never focused, not in Alt-Tab, on every workspace; clicks, hover, drags, scrolls and keys pass through an empty input shape to Wayland-native windows. It is hidden in the activities overview, below Shell modal dialogs and notification banners, and covered by the lock screen; all acceptable for an indicator.
- **Selection.** Only when the X server is XWayland (the `XWAYLAND` extension) and a compositing manager owns `_NET_WM_CM_S<n>` (ARGB needs compositing; Mutter owns it), and only after layer-shell failed, so wlroots and KDE keep layer-shell and a real X11 session (where upstream's own Electron overlay runs) is never picked. `CU_OVERLAY_BACKEND=x11` forces it for tests. The feature is opt-in: the wlroots and KDE bridges do not carry it (with it the static demo binary grows from 1.50 to 1.82 MiB on x86_64, from 1.27 to 1.55 MiB on aarch64; the x11 backend alone is 1.40 / 1.18 MiB); the GNOME bridge builds with `default-features = false, features = ["x11"]`.
- **Windows.** Four override-redirect windows per show, 32-bit TrueColor visual (the renderer's premultiplied BGRA is that visual's memory layout), background pixel 0, empty input shape (SHAPE), created bottom to top so they stack like the layer-shell subsurfaces: the glow or rim (the output), the badge, the press ring, the arrow. `WM_CLASS` / `WM_NAME` / `_NET_WM_NAME` `claude-cu-overlay` and `_NET_WM_PID` + `WM_CLIENT_MACHINE` let a bridge recognise the overlay; `_NET_WM_BYPASS_COMPOSITOR` 2 keeps Mutter from ever unredirecting the output-sized window. `_NET_WM_WINDOW_TYPE_NOTIFICATION`: for override-redirect windows the type only steers compositor treatment, and the EWMH notification type ("a notification bubble, override-redirect") fits a status indicator; no shadow was visible on the VM. The small windows start one logical pixel big: under native scaling Mutter never showed a window created at 1x1 X pixels, not even after it was resized (seen on the VM).
- **Opacity is the property.** `_NET_WM_WINDOW_OPACITY` does fades, capture hides and "not drawn" (an arrow off the output, a finished ring, no badge), so nothing is ever unmapped: measured against ScreenCast frames, an opacity change reached the stream in 35 ms median (32-44), a map took 140 ms. The output-sized window is drawn once per look and factor; the arrow, ring and badge windows are repainted (MIT-SHM `ShmPutImage`, `send_event` set) only when their content changes, and moved with `ConfigureWindow` (a whole-pixel move needs no repaint). A buffer is reused only after the server's `ShmCompletion` (like `wl_buffer.release`). Window move and content are separate requests, so a moving arrow is not atomic as on layer-shell (Mutter may show one frame of the old content at the new place; not looked for frame by frame).
- **No frame callbacks.** Mutter sends no `_NET_WM_FRAME_DRAWN` to override-redirect windows. An animating scene sends a sync marker after each present; the next frame is due when the marker came back and 16.7 ms passed, so the overlay never queues frames faster than XWayland processes them.
- **Sync markers.** A `ClientMessage` sent with an empty event mask to the overlay's own InputOnly window is delivered back to the overlay once the server processed everything before it: an asynchronous round trip on the event stream, polled like every other event.
- **Capture acks.** The round trip proves XWayland processed the opacity change, not that Mutter repainted. A sync that follows a present which made something invisible (or destroyed the windows) is reported 50 ms after its round trip; restores and other syncs need only the round trip. Measured on the VM over 40 rounds per scope (scope `all` with the rim and with the pulsing glow, scope `cursor`) and 20 per scope with native scaling: hide -> ack 50.4-63.6 ms, hide -> first clean ScreenCast frame 11-37 ms, no frame showing the hidden part after an ack, the clean frame at least 17.7 ms before its ack. Mutter sends a ScreenCast frame per change only, so the bridge's own settle after the ack is what guarantees the next frame it reads is a new one.
- **Coordinates** (`backend::x11::layout`, pure and unit tested). Without Mutter's experimental `xwayland-native-scaling`, X coordinates are global logical coordinates (factor 1; Mutter upscales X windows, blurry on fractional monitors). With it, X = logical x `s` on every monitor, `s` = the ceiling of the largest monitor scale, and the overlay draws at `s`. `s` comes from XSETTINGS `Gdk/WindowScalingFactor` (exact; measured 1 without native scaling, 2 with it), else a whole-number `Xft.dpi` / 96 (`Xft.dpi` includes the text scaling factor, measured 120 at text scale 1.25), else 1, unless the caller forces it. Logical output = RandR monitor / `s`; the windows go at logical x `s`, so a global logical point `L` lands on X pixel `round(L * s)`. `ready` and `outputs` report the logical rectangle, the RandR monitor name (the connector, as gnome-portal-bridge's `screens`) and `scale` = `s`: the per-monitor scale is not visible from X.
- **Stale RandR.** After a live factor change (native scaling switched, the largest scale changed) Mutter updates XSETTINGS, `Xft.dpi`, `_NET_DESKTOP_GEOMETRY` and the work areas, but XWayland's RandR keeps the old factor for every value Mutter did not resend: measured, native scaling switched on live left every monitor and the root at factor 1; then setting a monitor from 1.0 to 1.25 gave that monitor its new size at factor 2 but kept its factor-1 position, while the other monitor stayed at factor 1 entirely; an unplug and replug fixed only the replugged monitor. So each RandR monitor is fitted to its work area (`_GTK_WORKAREAS_D0`, one per monitor in Mutter's order, always current): size and position are each RandR's times `s/b` or unchanged, the smallest size containing the work area and a position keeping it inside, multiples of `s`, no overlaps, over every pairing of monitors and work areas (the fit changing the fewest values wins). Without work areas the uniform ratio `_NET_DESKTOP_GEOMETRY` / root size is used. One stderr line reports a correction. Arrow placement was measured on the VM (the arrow's white outline against a capture with the cursor hidden) within 1 px on both monitors with native scaling off, switched on live (all stale), per-monitor stale and after a replug; after a monitor scale change that took the factor from 2 to 1 it was checked by eye.
- **Layout changes.** RandR notifications and root `PropertyNotify` for `RESOURCE_MANAGER`, `_NET_DESKTOP_GEOMETRY` and `_GTK_WORKAREAS_D0` (and `_XSETTINGS_SETTINGS` on the settings owner) re-read the layout 250 ms after the last one: Mutter moves `_NET_DESKTOP_GEOMETRY` about 40 ms before gnome-settings-daemon updates XSETTINGS, and the layout in between is wrong (it produced a bogus `outputs` event before the debounce). A changed list goes out as `outputs`; the shown output moving or changing factor redraws everything at the new place; the shown output disappearing closes the windows (non-fatal `error` + `hidden`).
- **Physical layout mode.** With `scale-monitor-framebuffer` off and an integer scale > 1, Mutter's layout is physical pixels, XSETTINGS says 2 and X pixels are physical: from X this is indistinguishable from native scaling at factor 2, but the protocol's coordinates are then physical (factor 1). The GNOME bridge reads `layout-mode` from DisplayConfig and passes `Options { scale: Some(1) }` there.
- **Glow pulse: static by default.** Every pulse step changes the opacity of the output-sized window, which makes Mutter repaint the whole output. Measured gnome-shell CPU on the VM (10 s each, % of one core): no overlay 0, static rim 0.8, static glow 0.9, pulse at 30 Hz (layer-shell's rate) 187, at 10 Hz 200, at 5 Hz 156. On this software-rendered VM a full-output repaint is the dominant cost and lowering the rate barely helps, so the x11 glow shows upstream's base keyframe (its reduced-motion look) and does not pulse; `CU_OVERLAY_X11_PULSE_MS` (or `Options::pulse`) turns the pulse on, worth measuring on GPU-composited GNOME before making it the default. The badge's dot still pulses (a small window).
- **Cost.** Overlay / Xwayland / gnome-shell CPU on the VM: static rim 0 / 0 / 0.8 %, an arrow gliding at 60 fps 4.1 / 1.0 / 18.2 % at factor 1 and 9.9 / 1.2 / 21.3 % at factor 2 (384 px arrow buffers), glow + badge hold at factor 2 1.0 / 0.4 / 4.0 %.
- **Capture paths.** On GNOME the overlay windows are in every capture (portal ScreenCast and Shell screenshots) and nothing can exclude them, so the caller hides them with `capture` around each screenshot.

## Deferred

- **Pulse fidelity**: interpolating blur radii instead of an alpha multiplier would need a redraw per frame; not worth the CPU.
- **Cheaper shadows**: the lift shadow could be blurred at reduced resolution; about 0.7 ms per arrow frame at scale 1.5 today.
